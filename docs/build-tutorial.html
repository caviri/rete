Build a .rete, step by step

This tutorial builds one .rete file twice, once from Python and once with the command line, and then looks at what is inside it and what the build cost. The data is a synthetic knowledge graph of planetary systems. It is the graph from the JupyterLite notebook "Anatomy of a .rete", scaled by a size parameter, so you can run it in seconds and then make it a thousand times larger.

Every command and every output below was run with rete 0.5.0, which writes format 0x06 and reads 0x05 and 0x06. Outputs are trimmed with … where they are long.

You need Docker. The CLI and the Python package both run in containers, so nothing else is installed on your machine. If you already have a native rete command or a Python environment, use them and skip the Docker wrappers.

mkdir rete-tutorial && cd rete-tutorial
alias rete='docker run --rm -i -v "$PWD:/data" -w /data ghcr.io/caviri/rete-cli:0.5.0'
alias py='docker run --rm -i -v "$PWD:/data" -w /data python:3.12-slim'

On Windows Git Bash, set MSYS_NO_PATHCONV=1 first. In PowerShell, see the Quickstart for the wrapper function. The other install routes are on the install page.

1. Generate the graph

The generator is examples/gen_solar_kg.py. Save it next to your working directory. It has no dependencies and is deterministic for a given --systems and --seed.

The graph has the notebook's ontology: Planet, Moon and (new here) Star are subclasses of CelestialBody, and orbits has a domain and a range. The data starts with the notebook's eight bodies in the namespace https://example.org/solar/, followed by --systems generated systems, each with a star, two to six planets and up to three moons per planet. Bodies have a class, an English label, a radius in km and an inSystem link; planets and moons have an orbital period, and planets say whether they have an atmosphere. Nothing is typed CelestialBody directly.

py python gen_solar_kg.py --systems 100 -o solar.nt

6103 triples

The generator reports the triples it wrote on stderr. The first lines are the ontology; every body then has a few lines like these:

2. Build with Python

The Python package is rete-graph on PyPI; you import it as rete_graph. A Builder records what you ask for, and nothing is parsed until run(). The Python build tutorial covers every builder call. Save this as build_solar.py:

import rete_graph as rete

builder = (
    rete.Builder()
    .add_file("solar.nt")
    .card(
        title="Solar systems (synthetic)",
        description="A synthetic knowledge graph of planetary systems: the eight bodies of our own, then generated systems with a star, planets and moons. Made for the rete build tutorial.",
        license="CC0-1.0",
        version="1.0.0",
        created="2026-11-02",
        keywords=["synthetic", "tutorial", "astronomy"],
        example_queries=[
            "PREFIX s: <https://example.org/solar/> SELECT ?moon WHERE { ?moon s:orbits s:Mars }"
        ],
        extra={"pipeline": {"generator": "examples/gen_solar_kg.py", "systems": 100, "seed": 7}},
    )
    .derive_card()
    .pyramid(algo="types")
)
builder.run()
print(builder.stats)
builder.export("solar-py.rete")

derive_card() asks the Python builder for the same derived card profile the CLI writes (section 4). pyramid(algo="types") groups the graph's communities by rdf:type class. Run it:

py sh -c 'pip install -q --root-user-action=ignore --disable-pip-version-check rete-graph==0.5.0 && python build_solar.py'

{'statements': 6103, 'defaultTriples': 6103, 'namedGraphs': 0, 'terms': 3880, 'pyramidLevels': 1}

stats reports 6,103 statements over 3,880 distinct terms. export() wrote solar-py.rete. Now open it and ask questions. Save this as query_solar.py:

import rete_graph as rete

g = rete.open("solar-py.rete")
print(g.quads, "triples,", g.terms, "terms")

PREFIXES = """
PREFIX s: <https://example.org/solar/>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
"""

# 1. How many bodies of each kind?
rows = g.query(PREFIXES + """
    SELECT ?class (COUNT(?b) AS ?n) WHERE { ?b a ?class . ?class a rdfs:Class }
    GROUP BY ?class ORDER BY DESC(?n)""")
for r in rows:
    print(r["class"].value.rsplit("/", 1)[1], r["n"].value)

# 2. Which moons orbit Mars?
for r in g.query(PREFIXES + """
    SELECT ?moon ?name WHERE { ?moon s:orbits s:Mars ; rdfs:label ?name }
    ORDER BY ?name"""):
    print(r["moon"].value, r["name"].value)

# 3. Nothing is typed CelestialBody. With reason=True the query is rewritten
#    through the ontology (Planet, Moon and Star are subclasses of it).
q = PREFIXES + "SELECT (COUNT(DISTINCT ?b) AS ?n) WHERE { ?b a s:CelestialBody }"
print("asserted:", g.query(q)[0]["n"].value, "| with reasoning:", g.query(q, reason=True)[0]["n"].value)

# The file's own description.
print(g.card()["title"], "|", g.card()["extra"])
print(g.schema()["classes"][:2])

The third query is the point of the ontology. Asked plainly, it finds no CelestialBody, because none is asserted. With reason=True the engine rewrites the query through the subclass axioms (OWL 2 QL) and finds all 950, without adding a triple to the file. See Reasoning.

The fields fall into three groups; the Dataset Card reference lists all of them.

  • Curated, from your card file: title, description, license, version, created, keywords, example_queries, and extra. The extra object holds your own fields. Here it records how the graph was made: extra.pipeline carries the generator, the number of systems and the seed.
  • Derived, from the data: triple_count, term_count, the predicates and classes with their counts, vocabularies, datatypes, languages, class_links, the top hubs, and signals such as label_predicate and base_iri. The 20 starter queries are also derived, using this graph's own names.
  • Measured: the build record, described below.

signals.base_iri is the namespace most subjects share. It is derived from the data, and the starter queries use it to tell local IRIs from external ones. When the derived value is wrong, for example on a graph with very many namespaces, set base_iri in the card file. Python's Builder.card() has no base_iri keyword: it would end up in extra, so set it from a card file.

To curate a card after the build, change the JSON and run recard. It rewrites the card region of the file and leaves every data byte alone:

py python - <<'PY'
import json
c = json.load(open("solar-card.json"))
c["version"] = "1.0.1"
c["base_iri"] = "https://example.org/solar/"
c["description"] += " Systems are generated; only the first eight bodies are real."
json.dump(c, open("solar-card-v2.json", "w"), indent=2)
PY
cp solar.rete solar-curated.rete
rete recard solar-curated.rete --in-place --card-file solar-card-v2.json
rete verify solar-curated.rete

solar-curated.rete (in place): 20 starter queries (0 dropped), content hash b38ff62dbf5262ec1e50e4ef364be23e → a847f866566d3c07c1a6721ce8d2588c, 30031 B card in the card region's free space, no data byte moved; 0 s
OK — content hash matches, and every section digest (format 0x06)

The last line of recard's output is the summary above; it also prints one progress line per starter query on stderr. The file is the same length, because the new card and record fit in the card region's free space. rete card solar-curated.rete --json now shows version 1.0.1.

The card is inside the content hash, so editing it changes the file's identity (rete verify still passes; the hash is a new one). See Update a published card.

5. The schema

Every build writes a SCHEMA section, a few kilobytes that sit at the front of the file. It holds:

  • the class hierarchy from rdfs:subClassOf, with each class's depth;
  • rollups: instance counts at each level of that hierarchy, so a level-0 view counts all stars, planets and moons together as CelestialBody;
  • the lateral links between classes (planets orbits stars);
  • query_stats: for each predicate, how many subjects and objects it has and the largest fan-out in each direction;
  • characteristic sets: the groups of predicates that entities actually carry together.

The query planner uses query_stats and the characteristic sets to choose a join order without reading the index, and the explorer uses the hierarchy and rollups to draw the graph at several zoom levels before it fetches any triples. The format is in SPEC §7.5.

6. What happens during a build

rete build turns text into a file in a few steps. The phase names are the ones in the build record.

  1. Parse. The input is read as N-Triples, N-Quads, Turtle, TriG, RDF/XML or Jelly, optionally gzipped. For N-Triples, N-Quads and Jelly files the in-RAM build reads the input twice: pass 1 (parse+dictionary) collects the distinct terms, pass 2 (parse+encode) reads it again and replaces every term by its id, so the parsed text is never held in memory. Turtle, TriG and stdin take a different path that parses once and holds the statements.
  2. Dictionary. Each distinct IRI, literal and blank node is stored once. The terms are sorted, split by role into four sections (used as both subject and object, subject only, object only, predicates), and front-coded: each term stores the length it shares with the previous one plus the rest. Ids are assigned in that order, so an id tells you the term's role. A triple is now three integers. Duplicate statements are dropped here; the record counts them.
  3. Indexes. The id triples are sorted six ways (SPO, POS, OSP, SOP, PSO, OPS), so every triple pattern, with whichever positions it binds, is a contiguous range of one index. Each index is cut into tiles of about 64 KiB and each tile is compressed on its own with zstd. --permutations 3 keeps only the first three.
  4. Optional sections. The pyramid (communities of the graph), the label index and the text index are built from the same ids. The SCHEMA section is always built.
  5. Card. The profile is derived, the starter queries are run against the finished file, and the card and the build record are written.
  6. Write. The data is written at its final offset and hashed as it goes, then the front is written at offset 0, then the footer.

The layout that results (format 0x06, SPEC §4):

offset 0     +-------------------------------------------------+
             | HEADER, 128 bytes                               |
             |   counts, codecs, presence bits, content hash,  |
             |   where the card and the root are               |
128          +-------------------------------------------------+
             | ROOT BLOCK                                      |
             |   section table: kind, offset, length, digest   |
             +-------------------------------------------------+
             | CARD REGION                                     |
             |   card | build record | free space for recard   |
front_base   +-------------------------------------------------+
             | FRONT SECTIONS                                  |
             |   schema (query_stats, characteristic sets)     |
             |   leaf directories: dictionary, indexes, labels |
data_offset  +-------------------------------------------------+
             | DATA SECTIONS, one run per section              |
             |   dictionary chunks | index tiles | label blocks|
             |   text postings (if built) | pyramid (if built) |
             +-------------------------------------------------+
file_len-8   | FOOTER  06 00 00 00 "RETE"                      |
             +-------------------------------------------------+

A reader's first request is bytes 0 to 65,535 (SPEC §4.6). That one response holds the header, the root, the card, the planner statistics and, on a small file, every directory. The file length is in the header, so the client sends no HEAD. On a large file the directories do not all fit, and the query fetches the ones it needs as small ranges. It then fetches only the dictionary chunks and index tiles it touches, each a range request of about 64 KiB. Because every index is sorted, the tiles for one subject, or for one predicate, sit next to each other, and a scan is one contiguous read. Section 8 shows the result on a 106 MB file: a lookup reads about 3% of it.

Each section has a BLAKE3 digest in the root, and the content hash covers all of them and the card, which is what rete verify checks. The record is outside the hash. Older 0x05 files keep the same payload blocks but put the card and the directories elsewhere; rete convert rewrites one as 0x06.

7. Time and memory

This section measures the build at several sizes of the same graph. The figures are measurements; the one extrapolation is marked.

How it was measured. The generator wrote graphs of 101,770, 992,447, 9,910,209 and 29,762,321 triples (--systems 1,600, 16,000, 160,000 and 480,000). Each build ran in its own container started with --memory 4g, one at a time, using the 0.5.0 release binary. The wall time is the process's. The peak is the largest resident set size of the build process (getrusage, the same figure as /usr/bin/time -v), and the spill is the size of the --tmp-dir, polled every 0.25 s. The container's cgroup peak was 15 to 30 MiB above the resident-set figure in every run and is not shown. The host was a 32-thread Windows machine running Docker Desktop, with a separate 16 GB build container running on it the whole time, so take the absolute times as indicative and the ratios as the result.

Every run used --no-pyramid --label-index --card-file solar-card.json, because the memory-bounded build writes no pyramid. The build of section 3, with --pyramid-algo types, cost the same to within 5% in time and memory at 1 and 10 million triples (65.6 s and 1,093 MB against 63.0 s and 1,098 MB at 10 million).

You can read the same kind of figures from any file the CLI built. rete card prints the build record's wall time, peak memory and per-phase times:

rete card solar.rete | sed -n '/^      wall time/,/starter_queries/p'

What the numbers say

  • A build is linear in the number of triples. Without the starter-query measurement it took 4.4 to 5.4 seconds per million triples on this machine, from 1 million to 30 million (the 30 million figure is the bounded build). The 0.10 M row looks slower per triple because process start is a larger share of half a second. Peak memory in RAM is about 110 MB per million triples, and the file takes 10.7 bytes per triple with a label index. At 29.8 million triples the in-RAM build peaked at 3.1 GB in a 4 GB container. Extending the same line, it would stop fitting at about 35 to 40 million triples. That figure is an extrapolation, not a measurement.
  • Most of the time is parsing. The build record gives the phases. At 9.9 million triples in RAM without costs, in seconds: parse pass 1 (parse+dictionary) 15.1, parse pass 2 (parse+encode) 19.5, card_derive 15.4, labels+schema 2.0, index_permutations 0.6, dictionary_section 0.06, serialize 0.4, write 0.6. The six sorted indexes, which give the file its shape, are about 1% of the time.
  • Measuring the starter queries can dominate. With a card, the build runs the 20 starter queries against the finished file to record what each costs. At 0.99 million triples that took 14.3 s of a 19.2 s build (starter_queries 7.1 s, write 7.2 s; the CLI reference says the costs are measured again on the file as written). At 9.9 million it took 10.6 s. The queries are bounded, so the cost stops growing with the graph, but on a graph of a million triples it makes the build four times longer. --no-card-costs skips it, and the card then has no query_costs. Keep the measurement for a file you publish; skip it for a scratch build.
  • Python is fast and memory-hungry. The builder takes the whole input as text and returns the whole file as bytes, so it holds both: about 630 MB per million triples, against 170 to 200 for the CLI. It is faster per triple here because it measures no starter queries and records no phases. Use it up to a few million triples, then use the CLI.

The memory-bounded build

--memory-budget-mb N builds the same file with less memory. It reads the input once, cuts it into chunks sized from the budget, writes each chunk's sorted terms and id triples to --tmp-dir (zstd-compressed), merges the chunks into one dictionary, remaps the chunks to global ids, and builds each index with an external sort. The sections move from the spill into the output one by one and are deleted as they are copied. The CLI reference has the details. At any moment it holds a chunk or a merge buffer, not the graph.

What the measurements show:

  • The file is the same. The content hash of the 9.9 M file is 1c0f352778aa73111f1fff5667267cc5 for the in-RAM build and for the bounded builds at 256, 512 and 1500 MiB, with and without costs. At 29.8 M it is 8c828261561ec0f0db035834866ead95 for both builds. Only the build record differs.
  • It is not slower here. At 9.9 M it took 53 s against 63 s in RAM, and at 29.8 M 138 s against 175 s. Its card derivation streams the sorted sections and is much quicker (1.4 s against 15 s at 9.9 M).
  • It needs disk. The spill peaked at 11 to 12 bytes per triple, about the size of the output: 114 MB at 9.9 M and 363 MB at 29.8 M. Put --tmp-dir on a disk with that much room.
  • Below a few million triples it saves nothing. At 0.99 M a budget of 512 used 330 MB, more than the 201 MB of the in-RAM build, because the merge has a fixed floor. A budget of 128 brought it down to 215 MB.
  • With a card, the budget does not cover the starter-query measurement. At 29.8 M under a budget of 512 the build finished its own work inside 473 MB (--no-card-costs). With costs the process peaked at 1,946 MB, because the measurement reads the finished file with its own cache. The build record does not include that step: it reports 493 MB for that run. For a hard memory limit, add --no-card-costs.

Use the bounded build when the in-RAM peak (about 110 MB per million triples, plus a margin) would not fit in memory, or when the graph is tens of millions of triples or more. It writes no pyramid, so a file that needs the community pyramid has to be built in RAM or re-pyramided afterwards with rete repyramid.

rete estimate projects the size, time and spill before you start. It reads the input and writes nothing. For the 9.9 M file, with --memory-budget-mb 512 --no-pyramid, it said 47.5 to 71.3 MB, 20 to 34 s and a 2.1 GB spill. The build took 43 to 53 s, wrote 105.9 MB and spilled 114 MB. Use it for the order of magnitude of the time. It does not model the label index or the card, and its spill figure was 18 times too high here.

8. Use the file over HTTP

A .rete file needs no database server. Any host that answers Range requests with 206 Partial Content can serve it, and the client reads only the bytes a query needs. Hosting your .rete lists what a host must support and has recipes for R2, S3, Zenodo and GitHub Pages.

The 91 KB file from section 3 is too small to show this: a remote file of at most 8 MiB is read whole after the first request. So this section uses the 9.9 million triple graph from section 7, built with the same flags as before (106 MB):

py python gen_solar_kg.py --systems 160000 -o solar-big.nt
rete build solar-big.nt -o solar-big.rete --card-file solar-card.json --pyramid-algo types --label-index

To try it without a hosting account, serve the working directory with the repository's range-aware dev server, scripts/range_server.py (Python's own http.server ignores Range). Here it runs in a container:

docker run -d --name tut-range -p 8000:8000 -v "$PWD:/srv:ro" -w /srv python:3.12-slim python range_server.py 8000 /srv

(Copy range_server.py into the directory first. When the CLI itself runs in Docker, as here, the host is host.docker.internal; a native rete uses 127.0.0.1.) Check that ranges work with a GET. The check in Hosting uses HEAD, which this dev server answers with a plain 200:

9. Optional flags

These change what the file contains. Each is off by default. The CLI reference has the full list.

  • --label-index writes a label index: the display label of every labelled subject, sorted, so rete search <file> <prefix> and autocomplete read a few small ranges and no dictionary. Section 3 used it. Without the flag the file has no label index.

  • --text-index writes a word index over the literals, for rete search --contains <word> and fast SPARQL CONTAINS. It costs space: on the 100-system file it adds 15.8 KB to a 92 KB file (107,922 bytes in total). Full-text index has its scope flags.

    rete build solar.nt -o solar-text.rete --card-file solar-card.json --pyramid-algo types --label-index --text-index
rete search solar-text.rete --contains planet --limit 3

    <https://example.org/solar/S100_p0>
<https://example.org/solar/S100_p1>
<https://example.org/solar/S100_p2>

  • --named-graphs chooses how the graphs of an N-Quads or TriG input are stored. Format 0x06 has one layout, quad, so the flag is only there to refuse the old per-graph one. This tutorial's graph has no named graphs. See Named graphs in the quad index and SPEC §6.5.
