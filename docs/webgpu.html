Does a GPU help you find contradictions between two graphs?

When two knowledge graphs describe the same world with degrees of belief rather than crisp facts — CauseNet's extraction confidences, multi-source predictions, alignment scores — checking them against each other stops being symbolic clash detection and becomes arithmetic over [0,1]. Arithmetic is what a GPU is for. This page measures whether that actually pays off.

What the two kernels compute

A · disagreement, entity by entity

Two graphs each assert a fuzzy membership μ ∈ [0,1] over the same aligned entities — "G1 is 0.9 sure this is a Drug, G2 is 0.85 sure it is a Protein, and those classes are disjoint". The conflict degree is the Gödel t-norm min(μ_G1, μ_G2), and anything above a threshold τ is a violation. One min and one compare per entity: the GPU reads two floats to do almost no work, so it is bound by how fast the data arrives, not by the maths.

B · contradictions that only appear after you follow the chain

The interesting incoherences are not visible on any single edge. G1 says x causes y at 0.9 and y causes z at 0.8, which implies x causes z at 0.8 under max-min composition; if G2 asserts z causes x at 0.7, the two graphs disagree about causal direction even though no single edge contradicts. Finding those means computing fuzzy reachability — a max-min semiring SpMV, iterated: 

// one closure step; iterated k times with ping-pong buffers,
// so the graph is uploaded once and never leaves the GPU
@compute @workgroup_size(256)
fn main(@builtin(global_invocation_id) gid: vec3<u32>) {
  var i: u32 = gid.x;
  loop {
    if (i >= params.n) { break; }
    var best: f32 = x[i];
    let s = rowPtr[i]; let e = rowPtr[i + 1u];
    for (var k: u32 = s; k < e; k = k + 1u) {
      best = max(best, min(val[k], x[colIdx[k]]));   // max-min semiring
    }
    y[i] = best;
    i = i + params.stride;
  }
}

This is the same GraphBLAS primitive the academic GPU-SPARQL systems are built on, and it is where the arithmetic intensity lives: every edge is touched k times against resident data. On the largest configuration that is 256 million edge-visits in 16 ms.

What this means for rete

  • Stage once, run many. Upload throughput measured ~2.2–2.4 GB/s, and it dominates every large configuration. A single one-shot check wastes the GPU; a coherence session that uploads the aligned edge slab once and then sweeps disjointness, asymmetry, k-hop closure and thresholds against the resident copy approaches the compute-only numbers.
  • Pick the operation, not the hardware. A 2.2× ceiling and a 17× win came from the same GPU on the same data. Arithmetic intensity decided it.
  • This is not an argument for GPU SPARQL. Remote .rete queries are bound by HTTP range round trips, and local ones finish in single-digit milliseconds — below the latency floor of a GPU round trip. Whole-graph coherence is the opposite shape: batch, seconds-scale, one small answer at the end.
  • On memory: this adapter caps a single buffer well below the 4 GiB wasm32 heap. Any capacity win comes from using many buffers, not one large one — and rete's lazy tiles and chunked dictionary already keep 17 GB files queryable inside that heap.

Caveats — do not over-read these numbers

  • The baseline is JavaScript, not wasm. Wasm would likely be 1.5–2× faster, so discount accordingly; kernel B still lands around 8–9× end-to-end.
  • The graph is a uniform random digraph. Real causal and citation graphs are power-law, and one-thread-per-row will suffer load imbalance on them. This number needs re-measuring on a skewed degree distribution before anyone trusts it on real data.
  • The reference GPU is a high-end discrete card. Integrated GPUs will be far less dramatic — which is exactly what the button above is for.
  • The cost of getting data out of a .rete is not measured here. Decoding tiles and materialising a columnar slab is plausibly larger than both the CPU and the GPU numbers on this page. That is the next thing to measure, and it could sink the whole idea.
