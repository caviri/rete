How a remote graph is queried lazily

Remote datasets (e.g. wikidata-1GB, ohm-full) are never downloaded whole — each query fetches only the dictionary chunks and index tiles it touches.

The self-describing card

Each .rete embeds a small card: curated metadata (title, license, source) plus auto-derived stats — datatype/language histograms, the effective schema (class→predicate→class), top hubs, geo/temporal extents, and a schema pyramid with per-semantic-zoom-level type rollups. A remote reader fetches just the header + card in two HTTP ranges (~10 KB) to learn a multi-GB graph's shape and legend without ever touching the triple index.

Query helpers: label decode & entity finder

Two aids sit by the editor and never change what a query does — they only read and write the query text:

  • 🏷 Labels floats a human-readable name over each IRI: wd:Q100001 reads as Bemelen, wdt:P625 as coordinate location. Names come from a built-in vocabulary, predefined per-dataset hints, and a live rdfs:label / skos:prefLabel lookup.
  • 🔎 Find an entity turns a name you type into its IRI through rete's bounded label index (prefix_search — a binary search, never a full scan); click a hit to drop its <IRI> in at the caret.

Both are lazy-mode native: on a remote .rete they fetch only the few label tiles they need over HTTP range — a small spins while those bytes arrive.

Evaluation strategies

Whole index
The default and the reference answer. Evaluates against the full SPO/POS/OSP permutation indexes with the complete engine — every supported SPARQL form and feature. When in doubt, use this.
Progressive summary
A contract, not a speedup: answer exactly from the pyramid summary — community structure and per-predicate counts, fetched in ~3 small range reads — and never touch the triple index. Only shapes the summary can answer qualify (counting triples or a predicate's total, ASK-style existence). A query that returns values (titles, scores, IRIs) needs dictionary and index bytes, so it falls back to the whole index — and says so in a banner. The Progressive Metadata panel shows the exactness, bytes, and range reads of a summary-served answer.
Round (split by community)
The pyramid is built by repeated Louvain clustering: round 0 is the finest partition (many small communities); each higher round merges communities into coarser "clusters of clusters", up to the top of the dendrogram. The Round field picks which level the split uses — fewer, bigger partials at higher rounds; more, smaller ones at round 0. Left empty, it uses the same round the file build chose for its ~64 KiB tile budget. The answer is identical at every round; only the decomposition changes. The Explore tab visualizes these levels.
Split by community
Decomposes each basic graph pattern into subject stars, evaluates every star per pyramid community (the community's subjects pushed in as a VALUES binding), and recombines the partials with global hash joins; FILTER / UNION / OPTIONAL / MINUS recurse, paths and GRAPH evaluate globally inside the split, and ORDER BY / GROUP BY / LIMIT run once on the merged rows — so the rows are identical to the whole-index answer, with a per-community contribution table below the result. In this single-threaded page it illustrates the decomposition; natively the same partials are the seam for parallel evaluation. Refused only when nothing in the query can split (e.g. a pure property path).

🧠 Reasoning (OWL 2 QL)

With Reason on, the query is rewritten so it also returns the answers your ontology entails — nothing is precomputed or stored; it's derived from the raw data at query time. Opt-in: off means exact match.

What it adds
rdfs:subClassOf / subPropertyOf, domain / range, and owl:inverseOf entailments. Example: with it on, ?x a :Aves matches every bird occurrence through the taxonomy; with it off it matches only rows typed :Aves directly (often none).
How it works — and why it stays fast
A class atom ?x a C is rewritten into a subClassOf* path traversal — not a UNION of every subclass — so a deep taxonomy never blows up combinatorially. The path is goal-directed, so over a remote-lazy dataset it only range-fetches the hierarchy edges it actually walks.
What it costs
Effectively nothing when a query doesn't touch a hierarchy — the rewrite is a no-op. When it does, it costs about the same as writing the equivalent property-path query by hand. It changes the answer (asserted → entailed), which is exactly why it's a deliberate toggle rather than always-on.
Scope
The OWL 2 QL / DL-LiteR profile — a documented subset, not full OWL DL. For a one-shot logical-coherence check (disjointness, functional-property and sameAs clashes), see rete reason in the CLI.

⛁ All graphs (union default graph)

With All graphs on, this file is mounted as if its default graph were the union of the default graph and every named graph — a pattern outside GRAPH then matches data wherever it lives. The query text never changes; the dataset it runs against does. Off by default; announced in the result line on every run it changes.

Why it exists
Many converted files keep all their data in named graphs, so the standard answer to SELECT … WHERE { ?s ?p ?o } is 0 rows — correct, but a dead end. This toggle is the union default graph mode Virtuoso, GraphDB and Jena TDB offer as a store-level switch: query every graph as one merged graph without rewriting anything.
Not standard SPARQL
The SPARQL standard says a pattern outside GRAPH matches only the default graph. This mode deliberately departs from that — which is exactly why it is opt-in, visible while on, and every result it changes is stamped "⛁ union default graph (non-standard)".
What it does not affect
A query with its own FROM keeps its FROM dataset. GRAPH ?g { … } still enumerates and filters named graphs exactly as before. Federated (multi-source) runs and live SPARQL endpoints are untouched — they keep standard semantics and the result line says so.
What it costs
The engine materializes the merged index for the run. On a remote file with many named graphs the first union run can fetch a large share of the file — the merge must visit every graph (nkod.rete, 31,974 graphs: ~64 MB of a 68 MB file). Later union runs re-merge from this session's cache: seconds of compute with 0 new bytes, which the status line reports. A file with no named graphs is unaffected, and the common converted shape — empty default graph, exactly one named graph — stays a zero-copy borrow.

Output views — how to query for each

Each view renders one result a different way. Write your query so the columns the view needs are in the SELECT (or use a CONSTRUCT).

Table
Any SELECT, ASK, or CONSTRUCT — the default.
Cards
The same rows as Table, but one card per row with the fields stacked — media renders full-width, so it reads well on a phone. Cards flow as a masonry on a wide screen. The ⚙ Fields button picks how each field renders (including Image, IIIF, PDF viewer, Page preview, Markdown, Map, 3D, Audio, Video and Spin) — the same choices as a table column's header dropdown.
Graph
A CONSTRUCT { ?a ?p ?b } …, or a SELECT with ≥ 2 variables: 2 vars draw v1 → v2 ("related") edges; 3 vars are read as (subject, predicate, object). A one-variable select has nothing to connect.
Map geometry
A SELECT that binds a variable to a geo:wktLiteral — e.g. ?w via geo:hasGeometry/geo:asWKT ?w. POINT / LINESTRING / POLYGON / MULTI* all plot in an offline equirectangular view (no tiles), auto-fit to the geometries; the first non-geometry column becomes each feature's hover label. Available on any query — if the result has no geometry you'll get a short note (so a federated or unexpected geometry still maps).
Time year / date
A SELECT that binds a variable to xsd:gYear, xsd:date/xsd:dateTime, or a plain year integer (e.g. ex:year ?y). Renders a GitHub-style multi-year heatmap — cell colour = number of items in that year/bucket, hover lists them; spans bucket automatically and negative years read as BCE. The other selected column(s) are the tooltip items. Available on any query — if the result has no dates you'll get a short note.
TTL / JSON-LD
A CONSTRUCT query — these serialise the constructed triples. A SELECT has no triples to serialise.

Map, Time and Graph render SELECT bindings, so include the geometry / year / edge columns. Run them under Whole index or Split by community — Progressive answers only from the pyramid summary, with no per-row geometry or dates to plot.

Pick how each field renders on the cards. Auto detects images, IIIF manifests, PDFs, 3D meshes, audio/video and WKT geometry from the value. Force Page preview for a sandboxed page thumbnail or Markdown for a formatted literal. Changes apply live.
